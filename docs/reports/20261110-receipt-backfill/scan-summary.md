## 判定规则

分类只看可机械核验的四件事：结论字段、日志判定行、计数一致性、时间窗口。

| 桶 | 判定条件 | 处置 |
|---|---|---|
| `rejected_system_path` | 证据目录位于回收站（`$RECYCLE.BIN`） | 拒收 |
| `rejected_no_window` | 无开始时间 | 拒收 |
| `rejected_no_files` | 无任何证据文件 | 拒收 |
| `rejected_no_result` | 结论字段为空且日志无判定行 | 拒收 |
| `pending_no_result_verdict` | 结论字段为空，但日志有 `[RESULT] 判定:` 行 | 待取回后按判定行重建 |
| `pending_verdict_conflict` | 推断结论与日志判定行不一致 | 待人工核对，回执只能记 blocked |
| `pending_totals_mismatch` | `total != pass + fail` | 待核对计数口径 |
| `pending_no_verdict` | 结论字段有值但日志无判定行 | 待取回交叉校验 |
| `candidate_consistent` | 结论、判定行、计数三者一致 | 可生成候选回执（仍需取回原始产物） |

`reject` 表示现在就能判定不可用；`pending` 表示缺口可以靠取回证据补上；`candidate` 表示扫描层面自洽，但仍不足以转正式回执。

## 逐桶处置理由

**系统路径 83 行（拒收）**。证据目录落在回收站里，典型如 win000/win002/win004 的 `S-1-5-21-…-500` 目录。回收站内容会被清理、可被还原覆盖，不能作为运行证据。

**无时间窗 606 行（拒收）**。没有 `started`，无法界定运行窗口，也就无法与串口日志、固件版本对时。bszT14 上包括两个 NAS 验证任务与若干编排演练目录——它们本身有产出，但没有机器可读的时间字段，回执无从锚定。

**无结论 2127 行（拒收）**。结论字段为空且日志尾部没有判定行。test-101 的 496 行全部属于这一类：证据目录在测试日志服务器上，产物只有数据文件，没有判定语义。bszT14 的 1024 行多为编排演练与中间态目录。

**仅判定行 8 行（待取回）**。win006 的 8 条 `cskflashtest_*_burn-wake-asr_1rounds`：结论字段没解出来，但日志判定行明确写了 PASS。这是最容易被误判成"成功"的一类——扫描器给 null 是保守的，正确做法是取回 tool.log 复核后再按判定行重建回执。

**判定冲突 1 行（待核对）**。win009 `20261014_163403_wake_interval`：扫描器按目录名与文件词频推断为 PASS，而 tool.log 判定行写的是 `任务=BLOCKED 完成=0 异常=0 原因=初始化或日志等级恢复未通过: initialization marker missing`。同一行里"通过 1 个用例"与"任务 BLOCKED"并存，说明用例级通过与任务级判定不是一回事。本行已转候选回执（`run-20261014-163403-win009-wake-interval`，result=blocked），并在回执里把责任层落在扫描工具上。

**计数矛盾 16 行（待核对）**。`total` 不等于 `pass + fail`，例如 bszT14 上 tcl003 的四个运行在扫描时被记成 `10/10/7`、`10/10/8`——通过数等于总数却又有失败数。这类矛盾说明扫描器把不同层级的计数混在一起取，回执必须以本机原始 `summary_final.json` 为准（本任务已用原始文件重建，见 `row-ledger.csv` 与本机回执的对比）。

**无判定行 6205 行（待交叉校验）**。结论字段有值但日志里找不到判定行，绝大多数是 bszT14 上的 agent 任务目录（目录名是 uuid，`result` 由目录结构推断）。这批不是设备运行记录，只能作为"曾有这个目录"的线索。

**一致 4 行（候选）**。win009 的 4 条：结论 PASS、判定行 PASS、计数 1/1 一致。其中 `v15-u1-command-20261022_103328` 已转候选回执（`run-20261022-103329-win009-v15-u1-command`）。仍然只能记 `needs_review`：cases.csv、results.csv、tool.log 都还在目标机上，哈希无法本机复算。
